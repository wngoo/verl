## What is verl

verl (Volcano Engine Reinforcement Learning) is a flexible, efficient RL training library for large language models (LLMs). It implements the HybridFlow programming model with a single-controller architecture running on Ray. It supports FSDP/FSDP2 and Megatron-LM for training, and vLLM/SGLang/HF Transformers for rollout generation.

Linting uses `ruff` (line length 120). Type checking uses `mypy` (mostly silent except for specific modules like `verl.trainer.config.algorithm`, `verl.trainer.ppo.core_algos`, `verl.workers.reward_manager`).

## Testing

```bash
# Run CPU tests (no GPU required)
pytest tests/test_base_config_on_cpu.py
pytest tests/**/*_on_cpu.py

# Run a single test file
pytest tests/trainer/ppo/test_core_algos.py

# Run with verbose output
pytest -v tests/path/to/test_file.py
```

Test layout under `tests/`:
- `tests/<module>/` — mirrors `verl/<module>/` structure
- `special_distributed/` — multi-GPU tests
- `special_e2e/` — end-to-end training/generation tests
- `special_sanity/` — quick sanity checks (also run as pre-commit hooks)
- `special_standalone/` — tests needing dedicated environments
- `special_npu/` — NPU-specific tests
- Files ending in `_on_cpu.py` run on CPU; all others assume GPU

## Architecture Overview

### Programming Model

verl uses a **single-controller** model: a central Ray-based Python process (the trainer) orchestrates distributed workers. Workers are grouped into `RayWorkerGroup` instances and managed via `ResourcePoolManager`. Communication between controller and workers uses `DataProto`.

### Core Abstractions

- **`DataProto`** (`verl/protocol.py`): The universal data container for passing batches between components. Wraps `TensorDict` tensors plus a `non_tensor_batch` dict. All inter-component data flows through `DataProto`.

- **`BaseConfig`** (`verl/base_config.py`): Frozen dataclass base for all config objects. Implements dict-like interface for Hydra/OmegaConf integration. Fields are immutable by default unless listed in `_mutable_fields`.

- **`Worker`** (`verl/single_controller/base/`): Base class for all distributed workers. Decorated with `@register` to expose methods to the controller.

### Key Components

**Trainer** (`verl/trainer/ppo/ray_trainer.py`): The main PPO/GRPO training loop. Coordinates actor, critic, reference, and rollout workers. Entry point is `verl/trainer/main_ppo.py`.

**Workers** (`verl/workers/`):
- `fsdp_workers.py` — FSDP/FSDP2 backend workers for actor, critic, reference
- `megatron_workers.py` — Megatron-LM backend workers
- `actor/` — actor model logic (DP and Megatron variants)
- `rollout/` — rollout generation (vLLM, SGLang, HF)
- `critic/`, `reward_manager/`, `sharding_manager/` — other worker types

**Config** (`verl/trainer/config/`): Hydra YAML configs. Main entry points are `ppo_trainer.yaml` and `ppo_megatron_trainer.yaml`. The `_generated_*.yaml` files are auto-generated by `scripts/generate_trainer_config.sh` (run via pre-commit hook `autogen-trainer-cfg`) — do not edit them manually.

**Single Controller** (`verl/single_controller/`):
- `base/` — abstract Worker base and dispatch decorators
- `ray/` — Ray-specific RayWorkerGroup and ResourcePoolManager

### Algorithm Implementations

Core RL algorithms live in `verl/trainer/ppo/core_algos.py` (PPO, GRPO, advantage estimation). Additional trainers in `verl/trainer/` follow the same pattern.

### Training Backends

- **FSDP**: `verl/workers/fsdp_workers.py` — uses PyTorch FSDP/FSDP2
- **Megatron-LM**: `verl/workers/megatron_workers.py` — uses Megatron tensor/pipeline parallelism

### Rollout Engines

- **vLLM**: `verl/workers/rollout/vllm_rollout/`
- **SGLang**: `verl/workers/rollout/sglang_rollout/`
- **HF**: `verl/workers/rollout/hf_rollout.py`

## Contribution Policy (from AGENTS.md)

Before opening a PR:
1. Check for duplicate PRs: `gh pr list --repo verl-project/verl --state open --search "<keywords>"`
2. Do not open one-off PRs for tiny isolated edits — bundle mechanical cleanups with substantive work
3. AI-assisted PRs must include: why it's not a duplicate, test commands run, statement that AI was used
4. A human must review every changed line and run relevant tests

Do not modify code in domain areas listed in `AGENTS.md` without reading the linked domain-specific guide first.

## Important Conventions

- Device API: use `verl/utils/device.py` helpers (`get_torch_device`, `get_device_id`, etc.) rather than direct `torch.cuda.*` calls — enforced by `check-device-api-usage` pre-commit hook
- DataProto usage in `verl/workers/engine` is validated by `check-dataproto-usage` pre-commit hook
- All new Python files need the Apache 2.0 license header — enforced by `check-license` hook
- YAML config comments must appear above each field (not inline) — enforced by `autogen-trainer-cfg` hook
- The `recipe/` directory is a git submodule (`verl-recipe`); initialize with `git submodule update --init --recursive recipe`
